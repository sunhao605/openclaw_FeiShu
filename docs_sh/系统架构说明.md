# OpenClaw 系统架构说明

> 本文基于仓库源码顶层结构梳理，分析粒度为「目录 / 模块级」，不深入到函数级。
> 仓库：`myopenclaw`（OpenClaw，pnpm workspace 管理的 TypeScript ESM monorepo，版本 2026.8.1）。

---

## 1. 产品定位与整体设计思路

OpenClaw 是一个**自托管的个人 AI 助手平台**（"Multi-channel AI gateway with extensible messaging integrations"）。它的核心设计思想可以概括为一句话：

**一个常驻 Gateway 进程作为系统中枢，统一编排模型提供商、Agent 会话、消息渠道、工具、定时任务，并通过类型化的 WebSocket/HTTP API 向各类客户端（Web UI、CLI、TUI、移动/桌面 App）提供服务；所有外部能力（LLM、IM 平台、TTS、搜索等）通过 manifest-first 的插件体系接入。**

整体架构模式：

| 架构模式                             | 体现                                                                                                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **单体中枢（Hub）模式**              | 所有客户端、渠道、外部服务都汇入 Gateway（默认 `127.0.0.1:18789`），单端口复用 HTTP + WebSocket                                                         |
| **插件化微内核**                     | 核心（`src/`）保持插件无关；~145 个能力插件（`extensions/`）只能通过公开 plugin SDK + manifest 接入核心                                                 |
| **Manifest-first 控制面/运行面分离** | 插件的发现、setup、配置校验、激活规划完全由 `openclaw.plugin.json` + package.json `openclaw` 块驱动，**不执行插件代码**即可完成；运行面按需惰性加载注册 |
| **分层依赖，自上而下**               | `infra/` + `config/` 为底座 → 数据/安全层 → 模型层 → Agent 运行时层 → 渠道/插件层 → 服务入口层（gateway/cli/tui/daemon），底座不反向依赖上层            |
| **状态 SQLite 优先**                 | 运行时状态、队列、注册表、插件 KV 等一律存 SQLite（共享库 `state/openclaw.sqlite` + 每 Agent 库），禁止散落 JSON 边车文件                               |

## 3. 系统入口与启动链路

### 3.1 CLI 启动链（后端入口）

```
openclaw.mjs（Node 版本校验 + compile cache 决策）
  └─ src/entry.ts            CLI 进程真正入口：argv 规范化（Windows 兼容）、respawn 决策、
                             root help/version 快速路径、启动 trace
      └─ src/cli/run-main.ts Commander 命令注册与分发（命令编排中枢）
          ├─ gateway 子命令 → src/cli/gateway-cli/register.ts
          │     └─ run.ts / run-loop.ts（解析 bind/auth/tailscale 参数、获取 gateway 锁、
          │        常驻运行循环、处理重启信号/drain/热更新 respawn）
          │           └─ 动态加载 src/gateway/server.ts → startGatewayServer()  ← 常驻服务启动点
          ├─ daemon 子命令  → src/cli/daemon-cli/（launchd/systemd 服务化安装）
          ├─ cron / fleet / capability 等子命令 → src/cli/*-cli/
          └─ 库调用入口    → src/index.ts → src/library.ts（loadConfig 等，供外部库消费者）
```

关键入口文件清单：

| 入口         | 文件                                                                                                              | 职责                                        |
| ------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 可执行包装器 | `openclaw.mjs`                                                                                                    | 版本校验、运行时探测（Node/Bun）、转发 dist |
| CLI 进程入口 | `src/entry.ts`                                                                                                    | argv 处理、compile cache、respawn、trace    |
| 命令分发     | `src/cli/run-main.ts`                                                                                             | Commander 注册全部子命令                    |
| Gateway 启动 | `src/cli/gateway-cli/run-loop.ts` → `src/gateway/server.ts`（惰性门面）→ `src/gateway/server.impl.ts`（完整实现） | 启动常驻 Gateway                            |
| 服务化       | `src/daemon/gateway-entrypoint.ts`                                                                                | 已安装 daemon 的 gateway dist 入口解析      |
| 前端入口     | `ui/src/main.ts` + `ui/index.html`                                                                                | Control UI 启动                             |
| 前端构建     | `ui/vite.config.ts`                                                                                               | 产物输出 `dist/control-ui`                  |

### 3.2 本地开发拓扑

```
浏览器 ──开发──> http://127.0.0.1:5173  (Vite dev，仅托管前端静态资源)
   │                                   WebSocket 仍直连 ws://127.0.0.1:18789（需 allowedOrigins 配置）
   └──生产──> http://127.0.0.1:18789  (Gateway 直接服务 dist/control-ui SPA，同源直连 WS)
```

### 5.2 前后端集成方式

- **单端口复用**：Gateway 在一个端口（默认 **18789**）上同时提供 HTTP + WebSocket；WS upgrade 挂在同一 HTTP server 上，带 pre-auth 连接预算控制。
- **协议契约共享**：`packages/gateway-protocol` 定义类型化 schema 与运行时校验器，前后端共同引用，保证协议一致。
- **客户端库**：`packages/gateway-client` 提供握手/鉴权/重连/超时/session 投影；UI 使用其 `/browser` 导出。
- **生产模式**：浏览器访问 `http(s)://<host>:18789/` → Gateway 经 `src/gateway/control-ui-static.ts` 服务 `dist/control-ui` SPA；UI 把页面 origin 转为 `ws(s)://location.host`，**同源直连**。
- **开发模式**：Vite dev（5173，strictPort，无代理）仅托管静态资源；检测到 Vite 页面后把 WS 地址改写为 `ws://<hostname>:18789` 直连本机 Gateway（需 `allowedOrigins` 配置）。
- **远端连接**：支持 URL 参数指定 Gateway，如 `?gatewayUrl=ws://<host>:18789#token=<token>`，token 按 origin 作用域存 localStorage。

### 7.2 插件加载机制（manifest → loader → SDK 注册）

**插件侧**（以 `extensions/telegram/` 为例）：

- `package.json` 的 `openclaw` 块：声明入口（`extensions: ["./index.ts"]`）、`setupEntry`、完整 channel 控制面元数据（label、setup 字段 schema、CLI flags、docs 路径）。
- `openclaw.plugin.json`：插件 manifest（`id`、`channels`、`activation.onStartup`、`doctorContract`、`configSchema`）。
- `index.ts`：**声明式入口而非副作用注册**——渠道插件用 `defineBundledChannelEntry(...)` 按子面惰性指向各 `*-api.ts`；provider 插件用 `definePluginEntry({ id, register(api) })`，在 `register` 回调中向宿主注册能力。
- 依赖纪律：只能 import `openclaw/plugin-sdk/*` 及本包 barrel（`api.ts`、`runtime-api.ts`），禁止深引 core 内部或其他插件内部。

**核心侧**（`src/plugins/`，原则：控制面/运行面分离、manifest-first、保持惰性）：

```
发现 discovery.ts（bundled / workspace / global npm / package roots，区分 origin）
  → manifest 解析 manifest.ts + bundled-plugin-scan.ts（产出 PluginManifest，
    package-compat.ts 校验 plugin API 版本，activation-planner.ts 做激活规划——全程不加载运行时代码）
  → 加载 loader.ts → loader-runtime-load.ts 的 loadOpenClawPlugins()
    （loader-module-runtime.ts 惰性加载 → 执行 register(api)
     → registry-registrars-*.ts 按能力域登记 → activatePluginRegistry 激活为进程根 registry）
  → Gateway 启动走 gateway-startup-plugin-loader.ts，仅激活 manifest 声明或配置启用的插件
```

外部插件生态：`install-*.ts`（npm/git/path 安装）、`marketplace.ts`、`clawhub.ts`、安装记录存 SQLite；runtime 不装依赖，install/update/doctor 是修复点。bundled 与外部插件走**同一契约**，区别仅在发现 origin 与安全校验严格度。

## 10. 架构设计要点总结

1. **单中枢星型拓扑**：Gateway（`src/gateway/`）是唯一的常驻进程与中心枢纽——客户端（ui/apps/tui）、消息渠道、cron、hooks 全部汇入；单端口 18789 复用 HTTP + WS。
2. **微内核 + 插件注册表**：核心对插件完全解耦，插件仅经 `openclaw/plugin-sdk` 公开契约接入；bundled 与第三方插件同契约、同边界，仅发现来源与安全校验不同。
3. **Manifest-first**：插件的发现/setup/配置校验/激活规划不执行插件代码（`openclaw.plugin.json` + package.json `openclaw` 块），运行时按需惰性加载——这是整个扩展体系的关键架构决策。
4. **严格分层与惰性边界**：`infra/`+`config/` 底座 → state/secrets → llm → agents → plugins/channels → gateway/cli；重模块通过 `*.runtime.ts` 惰性边界与 `server.ts`/`server.impl.ts` 门面分离控制冷启动成本。
5. **前后端契约共享**：`gateway-protocol`（协议 schema）、`session-url-contract`、`workboard-contract` 等包保证前后端类型一致；`gateway-client` 是唯一推荐连接方式。
6. **状态纪律**：运行时状态 SQLite-only（共享库 + 每 Agent 库），schema 版本受控（state: 6、agent: 16），迁移统一走 `openclaw doctor --fix`，无运行时兼容 shim。
7. **设计取向**（来自 VISION.md）：单操作者个人助手、安全默认值优先、隐私自托管、渠道广覆盖、"能力即插件"。
